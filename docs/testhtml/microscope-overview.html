The Challenge

Why does this exist?

🌑

Hidden dependencies

As orgs grow, connections between engagement systems (LWC, Flows, Agentforce) and business logic are buried in code — invisible to architects and admins.

🔒

Tight coupling

Calling code references concrete Apex classes directly. Changing an implementation means changing every caller — across teams, packages, and releases.

📭

No audit trail

Service calls leave no record. Debugging failures, reconciling data, or proving compliance requires log archaeology.

🏛️

Governance bottlenecks

Regional or line-of-business variations must go through a single enterprise release. No way to safely pilot changes for a subset of users.

Core Concept

One name. Any implementation.

The caller references a single string — an Invocation Call. The framework resolves which service, method, and implementation to run based on metadata. The caller never imports or instantiates anything.

Architecture

Three-tier metadata model

📞
Invocation Side
LWC controllers, Flow actions, OmniStudio, Agentforce — the callers. Know only the Invocation Call string.
📋
Invocation__mdt
Translation layer. Maps caller → service name, version, method, and implementation version. No hard lookups — soft links by name only.
⚙️
Service Side
Three levels of service metadata, resolved at runtime.
🏢
Service__mdt
High-level business capability. e.g. "Pricing Service v1"
📐
Service_Method__mdt
Individual function with a fixed input/output contract (Method Iteration). Changing the schema requires a new iteration.
🧱
Service_Implementation__mdt
Points to the Apex class or Flow that runs. Multiple versions can coexist for A/B testing, rollback, and pilots.
Runtime

How a call flows through Microscope

1

Invoke

Caller passes Invocation Call string to ServiceInvocation

2

Retrieve

Query Invocation__mdt — apply permission filters, select matching record

3

Resolve

Query Service, Method, and Implementation metadata — check variants

4

Execute

Instantiate Apex class or launch Flow. Sync, Async, or Queueable.

5

Audit

Write Service_Framework_Audit__c record with input, output, timing, context

InvocationDetails

The central data envelope — carries user context, permission selections, input/output, timing, errors, and audit GUID through every step of the call.

IImplementation

Every implementation (Apex or Flow) implements this interface. The framework instantiates it via Type.forName() — zero static references from the framework to your code.

Versioning

Multiple live versions, zero flag days

Service Version

A complete re-implementation in a new namespace package. Allows reuse of class names across major versions.

Method Iteration

Version of the method signature. Increments when inputs or outputs change. All implementations for the same iteration share the same I/O contract.

Implementation Version

Version of the implementation logic. Multiple can run concurrently — enables A/B tests, pilots, and instant rollback.

No-Edit principle: never modify an existing implementation. Instead, create a new version. The old one stays deployed for instant rollback. Leave the Implementation Version blank on Invocation__mdt to always auto-select the latest.

Concurrent versions in production

v1 stays live for users without the pilot permission. v2 is routed to pilot users via an Invocation Permission. Both run from the same metadata, no branching in code.

Instant rollback

Remove the v2 invocation record. The framework falls back to the default record pointing at v1. No deployment needed.

Governance

Permission-driven routing

Multiple Invocation__mdt records can exist for the same Invocation Call. The framework picks the first one whose permission the user holds.

🚦
Release Permission
Org-wide gate — controls access to an entire feature release.
🌍
Invocation Permission
First segmentation — e.g. route EMEA users to a different implementation than US users.
🏢
Invocation Permission 2
Second segmentation — e.g. further split by line-of-business within a region.
🔐
Security Permission
Final access gate — applied after selection. Falls back to a less-specific implementation if not held.
✅
Default (no permission)
The catch-all record — any user not matched by a permission rule lands here.

Quiddity restrictions additionally prevent calls from wrong contexts (e.g. block a batch-only method from an LWC).

Resilience

Stubs for every environment

🧪

Scratch Stub

Temporary override via Custom Setting. Lets a unit test inject a known response without touching metadata. Cleared automatically.

📦

Absent Service Stub

Runs when the Service CMT doesn't exist in the target org — perfect for partial-code unlocked package deployments in scratch orgs.

🔴

Down Status Stub

Triggered when a service is marked unavailable (e.g. external dependency is down). Captures data, returns a graceful response.

🔌

Absent Connection Stub

Alternate method path when an external integration is unavailable in this environment (e.g. no callout in sandboxes).

Priority order: Scratch → Absent Service → Down Status → Absent Connection → Permission Override → Default

Observability

Complete call history, automatically

Dual Audit Points

Invoker Written immediately after invocation. Records input, permissions used, timing start.


Service Written when async execution completes. Updates the same record with output and final state.

Hierarchical call tracking

Each invocation gets a GUID with a position path:


ctx-123.1 — top level call

ctx-123.1.2 — nested child call

ctx-123.1.2.1 — grandchild (up to 5 deep)


Parent/child relationships stored on audit records — full call graph reconstructable.

Rerun

Stored input can be deserialized and re-invoked. Replay failed transactions after a fix.

Custom Serialization

Implement ICustomAudit to mask PII, summarize large payloads, or apply compliance transformations.

Build Map

Metadata graph of all Invocation → Service → Implementation links. Shows active, redundant, and orphaned connections.

AI Governance

Safe, audited AI invocations

Prompts and AI model calls flow through the same service framework as any other invocation — no special path.

Trust Layer Scores

Einstein Trust Layer safety scores are captured in the audit record on every AI call. Every prompt output is traceable.

Safety Thresholds

Three configurable thresholds:
Fatal Block + create Down Stub
Error Run alternate implementation
Warn Log only, proceed

Failover Algorithms

Given Order — run templates in sequence
Recent Safest — query audit history, run safest-first
Run All, Return Safest — execute all, return best score

AI prompts benefit automatically from Microscope versioning, regional routing, audit, and stubs — the same governance as any service call, applied to every LLM interaction.
